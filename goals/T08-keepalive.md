## 目标与范围

让用户分别开启指定 Route 和可控 Session 的定期有效请求，保留日期/天气动作，人工与已有任务优先。

## 实施步骤

1. 先实现自有 route 保活会话，再实现明确选中的 Session 空闲保活，最后接入可选天气动作；天气不成为核心初始化依赖。
2. 按目标分别持久启停、间隔、下次允许时间与最近真实成功。同 route 其他 Session 成功只刷新路由健康，不刷新目标会话。
3. 在统一准入中处理人工消息、活动轮次/队列、审批/输入等待、原生 Goal 活跃、Unknown 和配置变化。保活不得抢占已有工作。
4. 实现暂停与恢复、纯自有保活动作的取消；混入人工输入或归属不明时让路，停止后续自动输入。
5. 用单调时钟等待、UTC 持久化；休眠/重启后只处理一次到期动作。自有保活会话可以按已验证能力轮换，人工/任务会话保留原身份。
6. UI 展示保活目标、真实成功、延迟原因和成本可用性；空缺用量显示未知。迁入旧天气配置保留原间隔与权限来源。
7. 使用可控时钟和 Runtime fixture 覆盖竞争/计时，再用三类真实 CLI + 模拟供应商验证有效请求。

## 完成条件

- [ ] 三类 runtime 的 route 与目标 Session 保活路径可配置并实际验证。
- [ ] 人工活动、等待交互、原生 Goal 和 Unknown 都阻止保活注入。
- [ ] 成功计时按目标区分；失败不推进天气索引或更新时间。
- [ ] 暂停持久化，重启/迟到回调不重新启动；休眠后不补发所有 tick。
- [ ] 队列/容量不足显示延迟，不强杀任务满足保活倒计时。
- [ ] 相关状态/协议/浏览器检查通过，真实供应商效果未测部分明确记录。

## 收尾

按公共规则记录实际验证、未决事项和下一步。仅执行本工作包时，满足全部完成条件才完成当前原生 Goal；在 IMPLEMENT 总 Goal 内只更新本项进度并继续。

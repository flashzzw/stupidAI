## 一、先说你截图里的这种“11 个 Agent”：方向对，但不要让 11 个 Agent 同时工作

第一张图里的：

`code-smell-auditor`、`convention-guardian`、`data-calibrator`、`doc-syncer`、`frontend-verifier`、`gate-runner`、`multimodal-specialist`、`roadmap-researcher`、`runtime-verifier`、`test-author`、`worklog-recorder`

从产品设计角度很好。

但这里必须区分两个概念：

**Agent Profile ≠ 正在运行的 Agent Process。**

你完全可以安装 20 个、30 个这种“专家”，但真正执行一个项目时，不应该同时启动二三十个模型互相讨论。否则很快就会出现上下文爆炸、重复工作、互相改同一文件、验证循环、Token 成本暴涨。

你第二张图里的结构其实更接近我建议的形式：

> `general-purpose`
>
> `Explore`
>
> `coder`
>
> `reviewer`

我会进一步把整个系统收敛成 **4 个核心运行角色**：

**Lead / Coordinator** 负责理解最终目标、拆任务、依赖关系、决定交给谁，自己尽量不大量改代码。

**Explore / Researcher** 是只读型，用来搜代码、理解架构、定位 bug、查文档、做竞品/技术调查，可以并行很多个。

**Implementer** 才真正写代码。这里可以同时存在 `Codex CLI`、`Claude Code CLI`、`DeepSeek Harness Agent` 等不同 backend，但每个写代码任务应有明确的工作目录和修改范围。

**Reviewer / Verifier** 不负责主实现，检查 diff、编译、测试、功能、架构约束，然后决定“通过 / 打回”。

至于你第一张截图里的 `test-author`、`frontend-verifier`、`doc-syncer`、`data-calibrator` 等，我更倾向把它们设计为：

> **Agent Profile + Skill + Gate**

而不是长期存活的 Agent。

例如修改前端时，Coordinator 才临时启动 `frontend-verifier`；数据项目才启动 `data-calibrator`；准备合并时才运行 `gate-runner`。

这样 UI 上依然可以展示你截图里的 11 个专家，但运行层可能只有 2～4 个同时工作。

# 四、为什么我强烈建议所有 Codex / Claude Code 都直接跑在 WSL

AWS 的 CLI Agent Orchestrator 本身依赖 tmux，因此官方明确要求 macOS/Linux，Windows 本身不直接支持；但这恰好非常适合跑在 WSL。:chatgpt-content-reference{index="10"}

也就是说：

```text
Windows.exe
      │
      │ 只启动一次
      ↓
WSL Agent Runtime
      ├── codex
      ├── claude
      ├── dsh
      ├── git
      ├── python
      ├── node
      └── docker
```

而不是反复：

```powershell
wsl.exe codex ...
wsl.exe claude ...
wsl.exe codex ...
```

后者会给长程任务带来一大堆麻烦：

进程树、Ctrl+C/取消、PTY、HOME、PATH、环境变量、CLI Session、stdout 流、后台任务、子 Agent 全都更难管理。

最好在 WSL 里有一个常驻：

```text
agent-runtime-server
```

Windows UI 通过：

```text
http://127.0.0.1:xxxxx
ws://127.0.0.1:xxxxx
```

管理它。

这也是为什么 ZCode 的 Web/Server/Remote 架构很值得参考，而不是单纯照抄它的 Agent Prompt。

## 六、但是 DeepSeek Harness 的 Agent Teams 目前有一个我认为必须自己补的东西

就是：

# Git Worktree 隔离

DeepSeek Harness 的 Agent Teams 当前明确采用 **共享 cwd / 共享 checkout**。

官方设计说明甚至专门写到：

所有 Team Member 会看到彼此写入；`writeScopes` 只是冲突提示，并不是锁；Harness 本身**不会自动创建 Git Worktree**。:chatgpt-content-reference{index="12"}

这对于：

```text
Research Agent
Documentation Agent
Read-only Reviewer
```

问题不大。

但是对：

```text
Codex 实现 API
Claude 改前端
另一个 Codex 重构公共类型
```

很危险。

所以我会强制：

```text
Task A
↓
.worktrees/task-a

Task B
↓
.worktrees/task-b

Task C
↓
.worktrees/task-c
```

每个写 Agent：

```text
独立 branch
独立 worktree
独立 cwd
```

最终由：

```text
Integrator / Lead
```

统一：

```text
review diff
→ test
→ merge/cherry-pick
→ integration test
```

这个能力可以参考 Augani 的 Agent Orchestrator。它已经实现了 **one-writer-per-workspace、worktree、dependency ordering、review gate、detached job、heartbeat 和持久化 plan**。:chatgpt-content-reference{index="13"}

这一套对于“大项目长程任务”比“让 10 个 Agent 互相聊天”重要得多。

# 七、长程任务真正需要的不是更多 Agent，而是“外部状态”

这是很多 Multi-Agent demo 最大的问题。

真正需要持久保存的不是聊天记录，而是：

```text
Project
 └─ Run
     ├─ Goal
     ├─ Plan
     ├─ Decisions
     ├─ Tasks
     │    ├─ Task 001
     │    │    ├─ dependency
     │    │    ├─ assigned_agent
     │    │    ├─ worktree
     │    │    ├─ attempt
     │    │    ├─ result
     │    │    └─ verification
     │    └─ Task 002
     │
     ├─ Artifacts
     ├─ Git commits
     ├─ Tests
     ├─ Questions
     └─ Checkpoints
```

比如用 SQLite 就完全够了。

Agent 死掉没有关系。

Windows 重启没有关系。

Claude Code Session 没了也没关系。

因为重新启动后：

```text
SELECT unfinished_tasks
```

就可以恢复。

这才是真正意义上的“长程任务”。

# Windows / WSL Agent 工作台需求分析

日期：2026-09-30。状态：已纳入角色协作、开源研究及多执行配置/能力管理需求；明确多供应商并发隔离、每次执行选配 Skill/MCP/CLI 插件，并区分平台功能插件。底座、CLI 选择的委派方式与具体运行约束仍待确定。

本文从用户目标出发，不预设 Go、桌面框架、数据库、插件形式或开源底座。前一轮的 [源码研究](research-analysis.md) 与 [开源项目深度筛选](open-source-platform-survey.md) 用于判断可行性，不作为用户已经选定的产品方案。研究提出的验收细化与用户已确认决定分别标明；新旧实施路线的对应关系见 [实施计划](implementation-plan.md)。

页面结构、完整用户流程和异常交互见 [产品设计 V0.3](product-design.md)。配置事实和 Harness 原则见 [补充设计依据](harness-and-execution-config.md)，首批本机验证见 [实验报告](execution-capability-experiments.md)。其中新增默认值为可评审建议，不替代本文的已确认需求与待决事项；部分协议实验通过不等于对应产品需求全部满足。

## 1. 产品目标

建设一个类似 DeepSeek Harness 体验、能够通过插件持续扩展的 Windows 桌面工作台。用户给出开发目标，由 Lead / Coordinator 理解目标、组织任务及依赖并选择执行者；Explore、Implementer、Reviewer / Verifier 各司其职，最终交付可检查、经过验证的项目改动。四类角色及专家 Profile 都能选用 WSL 中的 Codex CLI 或 Claude Code CLI。

平台同时支持新建任务和接续已有 WSL 终端任务。当前 `codex-netcap` 的功能应作为平台中的一个功能插件纳入；平台主体不默认等同于当前项目。执行能够跨多轮持续进行，遇到中断可以恢复，需要人工决定时说明问题并等待处理。

每次 CLI 执行都能选用一份明确的执行配置，并选配 Skill、MCP 和原生 CLI 插件。多套供应商配置可以同时使用且保持会话身份与状态隔离。软件统一管理共享 Skill/MCP 以及 Codex、Claude 各自的 Skill/CLI 插件；平台功能插件用于扩展软件本身，与原生 CLI 插件分别管理。

用户希望减少三类负担：

- 环境操作：反复处理 Windows / WSL 的入口、目录、CLI 和图形工具之间的切换。
- 任务推进：反复提醒 Agent 继续、传递上下文、整理剩余事项和处理失败。
- 协作收尾：手工给多个 Agent 分工、避免互相覆盖、汇总结果和核对是否完成。

用户将此前的“自动编排”进一步明确为“Lead 驱动的角色协作”。拆分和协作判断由 Lead 作出，工作台负责执行这些安排、展示进展及维持已约定的运行约束；不预设必须搭建一个通用工作流编辑器。仍需用一个真实任务样例确认具体交付标准和规模。

## 3. 最重要的使用流程

### 场景 A：给出一个开发目标

1. 用户在 Windows 选择项目，能辨认对应的 WSL 环境和实际目录。
2. 输入开发目标、约束和完成条件，可以附已有需求或任务文档。
3. Lead 理解目标，按需安排 Explore 搜索代码和资料；能自行查明的事实自行查明，缺少关键决定时集中提出。
4. Lead 汇总发现，形成任务、依赖、执行者及验证安排；工作台展示这些安排，用户可以编辑和纠偏。
5. Implementer 在已授权的工作目录和修改范围内实现；工作台记录完成项、当前工作和阻塞原因。
6. Reviewer / Verifier 检查结果并执行 Gate；打回时由 Lead 安排实现者修复，缺少条件或超出约束时说明阻塞。
7. 汇总改动、验证证据、未完成部分和下一步，用户能够检查结果并继续讨论。

不把每一步计划审批设为默认负担。需要额外授权的操作以及用户设定的决策节点，单独处理。

### 场景 B：离开后回来继续

用户提交任务后关闭界面，再打开能看到执行进度；控制程序异常退出或电脑重启后，已完成事项、现有修改和待处理问题仍可追溯。系统核对原执行状态后继续，无法判定时明确提示，不重复启动同一项修改。

“关闭界面继续运行”和“电脑休眠/关机期间继续运行”是不同要求。本文只把前者及重新启动后的恢复列为建议核心；后者需要另一个持续在线的执行环境，尚未纳入范围。

### 场景 C：多个 Agent 共同交付

Lead 将工作分配给承担对应角色的 Agent，并提供必要上下文和交接材料。Explore 可以多实例并行；Implementer 的任务要明确工作目录和修改范围；Reviewer / Verifier 独立检查产物。相关任务按依赖推进，修改不能悄悄互相覆盖；Lead 负责汇总，不把收集来的对话直接当成最终交付。

四类角色表示职责分类，不要求固定四个常驻进程，也不规定每次任务都必须启动全部角色。并发数量受用户设定的容量与运行约束控制。

### 场景 D：用户接手

用户看到方向偏差后，能补充要求、暂停后续执行或转回终端。系统清楚显示哪些动作已经结束、哪些仍在进行，以及恢复后从哪里继续。已明确取消的任务不能自行重新启动。

### 场景 E：接续已有终端任务

用户已有在 WSL Codex 或 Claude 中开始的工作，希望从桌面工作台继续管理。系统应保留原会话的历史和项目上下文，并把后续工作纳入任务管理。仅复制一段对话并新开一个无关联任务，不能算完成该场景。

接续时要明确原终端与工作台谁负责继续输入，避免两边同时推进。两种交接方式都必须支持，且在 Codex 和 Claude 上分别验收：

- 实时接入：原 CLI 正在执行时，工作台能够连接该原会话、查看进展；用户能够切换到工作台操作，再返回终端。切换不创建第二份独立执行，不丢失原有工作。
- 暂停后恢复：原 CLI 暂停或退出后，工作台能够恢复同一会话及任务上下文，继续尚未完成的工作；不是从头生成一个无关联任务。

真实接入范围、CLI 版本，以及是否需要事先安装扩展或使用特定启动方式，必须在技术验证时明确披露。只支持工作台自己创建的会话返回终端，不能替代对独立已有终端任务的验收。若某种 CLI 的实时控制尚不能实现，应如实记录该需求未满足。

### 场景 F：以插件增加能力

用户安装或启用一个功能插件，例如当前项目提供的会话托管、探测或保活能力，在同一个工作台中配置、使用并查看状态。以后增加其他插件时，应能使用平台已有的项目、Agent、会话和任务能力，不要求再运行一套独立管理界面。

插件可以拥有自己的设置和功能入口；安装、启用、禁用、升级失败有可理解的状态。禁用时若还有关联任务，需明确选择或采用已约定的处理方式，不能无声丢弃任务与结果。首期不要求公开插件市场或不停机热升级。

## 4. 角色、执行后端与专家能力

术语见 [领域词汇表](../CONTEXT.md)。以下是用户明确的职责划分；示例中的技能与具体 Gate 是便于讨论的候选。

### 四类核心运行角色

| Role | 主要职责 | 工作范围 | 可选 Backend |
|---|---|---|---|
| Lead / Coordinator | 理解目标、拆任务、安排依赖、决定交给谁、汇总与沟通 | 主要负责协调，尽量不大量改代码；不把“少写代码”解释为用户已经要求绝对只读 | Codex CLI / Claude Code CLI |
| Explore / Researcher | 搜代码、理解架构、定位 bug、查文档、竞品/技术调查 | 对项目代码和业务数据只读；结果提供发现、证据和不确定项；允许多个探索者并行 | Codex CLI / Claude Code CLI |
| Implementer | 实现代码及其他项目改动 | 每项工作明确目录、修改范围和交接要求；并发写入需满足工作区约束 | Codex CLI / Claude Code CLI |
| Reviewer / Verifier | 检查 diff、编译、测试、功能与架构约束，给出通过或打回 | 不承担该项工作的主实现；发现问题交回实现者修复；条件缺失时明确无法判定 | Codex CLI / Claude Code CLI |

角色职责应在实际执行能力和结果检查中体现，不能只修改显示名称或提示词。运行编译、测试时可能产生缓存和测试产物，需要约定相应范围；这不授予 Reviewer 随意修改主实现的职责。

角色与 Backend 可以独立组合。例如 Lead 用 Claude、Explore 用 Codex、Implementer 用 Claude、Reviewer 用 Codex；也可以全部使用同一种 CLI，但保持各角色的任务上下文与责任独立。使用同一种 CLI 不等于实现者对自己的同一份输出自我批准。

### Agent Profile + Skill + Gate

| 层次 | 回答什么 | 示例 |
|---|---|---|
| Role | 这次承担什么职责 | Implementer |
| Backend | 实际使用哪个编码工具 | Codex CLI 或 Claude Code CLI |
| Agent Profile | 可复用的工作配置是什么 | `test-author` 的职责、工作指引、Backend 选择和关联能力 |
| Skill | 如何做这一类工作 | 测试设计、前端检查、文档同步方法 |
| Gate | 凭什么通过验收 | 相关测试通过、要求的检查完成且留有结果 |

专家 Profile 按实际工作归入四类角色，不形成另一套常驻角色体系：

| Profile 示例 | 对应 Role | Skill 示例 | Gate 示例 |
|---|---|---|---|
| `test-author` | Implementer | 为行为设计测试、构造测试数据 | 测试能捕获目标行为，相关测试通过 |
| `frontend-verifier` | Reviewer / Verifier | 浏览器交互和视觉验证 | 指定流程与展示条件通过，保留检查结果 |
| `doc-syncer` | Implementer | 根据实际行为更新文档 | 命令、示例及链接与当前实现一致 |
| `data-calibrator` | 依具体任务明确 | 数据规则与样本核对 | 校验规则满足且误差有证据；若需要修正数据，该任务归 Implementer |

每个专家 Profile 都能选择 Codex 或 Claude。配置中列出的 Skill/Gate 必须能在所选 CLI 的执行路径中实际使用；不同 CLI 不必有相同配置文件格式，但应交付相同的职责和验收语义。

新增的 CLI 执行配置独立于 Agent Profile：前者确定工具、原生配置来源、状态归属和供应商默认值，后者确定职责与工作方法。角色配置可以引用默认执行配置及 Skill/MCP/CLI 插件，但每次执行仍可显式调整允许调整的部分，并记录最终生效结果。平台功能插件不放入这份原生 CLI 插件选择器。

Gate 可以由确定性命令、测试、浏览器检查或 Reviewer 的证据判断组成，不必都创建额外 Agent。角色未启动不等于检查不需要运行；通过、打回、无法验证应分别记录。Implementer 的完成声明不代替 Gate，打回也不表示之前的改动应被删除。

典型协作过程：

```text
用户目标
  → Lead 理解与组织
  → Explore 按需调查，可并行
  → Lead 汇总发现并派发
  → Implementer 在明确范围实现
  → Reviewer / Verifier 检查，执行相关 Gate
      ├─ 通过：Lead 汇总交付或推进依赖任务
      ├─ 打回：Lead 把问题和证据交给 Implementer 修复
      └─ 无法验证：说明缺失条件，保持未验收
```

这是职责关系的说明，不要求所有任务采用固定步骤数；Lead 可按任务需要安排参与者，既定验收条件仍需满足。

### CLI 选择与运行中变更

已确认每类角色和专家 Profile 都可选 Codex/Claude。是否由用户固定选择，或允许 Lead 在候选集合中选择，正在澄清；不能据此默认允许任意自动切换。

建议规则：Backend 选择在启动一次工作时明确记录。修改 Profile 的默认值不悄悄改写在途工作；从 Codex 切到 Claude 应通过明确交接处理，而不是假设两者能共享同一个原生会话。跨 CLI 切换与此前确认的“原 CLI 会话接续”是两个不同需求。

## 5. 功能需求与可观察的完成条件

下表是目标能力草稿，不意味着所有项都必须同批实现。

| 编号 | 用户需要什么 | 完成条件 |
|---|---|---|
| R01 环境入口 | 在 Windows 选择 WSL 项目和编码工具 | 能看清执行环境、项目目录和工具；路径或工具不可用时指出具体问题 |
| R02 原生工具 | 使用 Codex CLI、Claude Code CLI 的实际能力 | 请求经过所选工具；使用哪份配置可以核对，不静默替换成另一个产品或账号 |
| R02b 已有任务接续 | 从桌面继续管理两类 CLI 已开始的任务 | 两类 CLI 分别通过实时接入、暂停后恢复；原会话身份、历史和工作上下文可追溯，原端与工作台不重复推进 |
| R03 目标与计划 | 输入大目标或任务文档，并调整执行方向 | 目标、约束、完成条件及计划能回看；进行中的任务不因文档外部变化被无声改写 |
| R04 持续推进 | 多轮执行，减少手工反复催促 | 尚有可执行且已授权的步骤时能继续；完成、阻塞或达到约束时有清楚的停止原因 |
| R05 角色协作 | Lead 理解目标、组织任务并协调另外三类角色 | Lead 的分工与依赖可回看；Explore 保持只读；实现有明确修改范围；Reviewer 独立给出通过/打回及证据；失败不解锁依赖 |
| R06 中断恢复 | 界面关闭、连接断开、程序重启后继续管理任务 | 已有结果保留；核对原执行、在途操作和未决交互后恢复；无法判定时显示待核对，不因启动成功就标空闲或盲目重复执行 |
| R07 人工控制 | 补充要求、处理问题、暂停、停止、恢复 | 显示真实执行状态；人工接手后停止自动争用；取消和恢复行为可解释 |
| R08 状态与提醒 | 快速知道进展、阻塞及需要我做什么 | 首页可识别进行中、需处理、已完成任务；详情可查证据；提醒不重复打扰 |
| R09 验证与交付 | 获得能审查的改动，而不仅是完成声明 | 展示改动和实际验证结果；通过、失败、未执行分开；未验收不标交付成功 |
| R10 运行约束 | 控制并发、执行时长及可观测用量 | 能设置约束、看到停止原因；无法统计的费用/用量明确标未知；无进展不无限重试 |
| R11 插件扩展 | 后续通过插件增加功能；当前项目能作为一个功能插件 | 至少一项当前功能以插件形式贯通界面、执行、状态与设置；无需为它复制整套平台；退出或禁用不会丢弃已有结果 |
| R12 桌面体验 | 在 Windows 统一完成派任务、看进度、审查和人工介入 | 有便捷入口；无需日常手工维护多个控制终端；环境未就绪时能够定位问题 |
| R13 插件管理 | 安装、启用、配置和更新功能插件 | 兼容性与加载错误可见；插件升级不静默清空任务数据；新增独立插件不要求修改其他业务插件 |
| R14 角色与 CLI 选择 | 四类角色以及各专家 Profile 均可选择 Codex/Claude | 四类角色分别验证两种 CLI，共八种组合；相应职责在实际执行中成立；不依角色硬编码工具 |
| R15 专家能力组合 | 保存和复用 Profile、Skill、Gate 的组合 | 专家能力按需使用；切换所选 CLI 后工作指引与验收要求仍生效；配置存在不等于常驻进程 |

以下为开源研究提出的验收细化，分别落实 R02/R02b、R06/R07、R05/R09、R11/R13，尚不表示已选定具体协议或实现：

| 编号 | 细化要求 | 建议的完成条件 |
|---|---|---|
| R16 能力与兼容性 | 知道当前 CLI、连接方式和插件实际支持什么 | 可以核对工具版本、执行位置与配置来源；新建、读取历史、原生恢复、实时观察和实时操作分别显示能力；不支持时说明原因，不静默新建或更换 Backend |
| R17 输入控制权 | 终端、工作台、Lead 与插件不会同时抢同一会话 | 可多端观察，但输入和自动调度有可核对的归属；交接和断连恢复不产生第二个独立执行者；人工接手后停止后续自动介入 |
| R18 工作区与产物保留 | 多个写任务不覆盖彼此，暂停或失败后成果仍在 | 同范围并发写入被隔离或串行安排；停止、崩溃、禁用插件不自动删除未提交修改；清理与停止分开，结果可审查 |
| R19 验证证据有效性 | 知道“通过”针对哪份改动 | Gate 记录被检查的产物版本、命令/检查、结果和限制；修复或后续改动后重新验证受影响条件；旧证据不自动批准新产物 |
| R20 插件与平台协作 | 插件复用平台会话和任务能力 | 明确会话、任务、调度及数据由谁负责；一个真实 netcap 功能贯通设置、执行和状态；重启、禁用、升级失败不双重调度或丢失数据 |

以下为本轮新增需求；具体实现机制须结合目标 CLI 版本验证：

| 编号 | 用户需要什么 | 完成条件 |
|---|---|---|
| R21 多执行配置并发 | 同一种 CLI 使用不同供应商和配置同时工作 | Codex 两份 CODEX_HOME、Claude 两份 settings 及各自明确的状态/环境绑定同时运行；会话、凭据来源和控制端点不串用，重启后仍回到各自原身份 |
| R22 每次执行选配能力 | 本次决定使用哪些 Skill、MCP、CLI 插件 | 新建、派发及继续前可查看/调整能力选择；明确继承项、插件带入项及不可覆盖项；预期选择与实际加载核对，不能把未选中的可选能力悄悄暴露给该执行 |
| R23 共享与专属能力管理 | 一处管理可复用资产及 CLI 专属能力 | 共享 Skill/MCP 可被两类 CLI 引用；Codex/Claude 专属 Skill/插件分区，记录来源、版本、兼容性和引用；更新不无声污染在途执行，MCP 定义共享不导致认证连接串用 |
| R24 两种插件分离 | 软件功能与 CLI 扩展不会混淆 | 平台功能插件和 CLI 插件分别展示所属宿主、安装位置、组成与生效范围；启停其中一种不暗中启停另一种或删除 CLI 会话 |
| R25 有效配置可追溯 | 知道本次究竟用了哪些配置和能力 | 保存执行配置快照与实际生效证据；原生配置继承、权限冲突和外部热更新可见；正常重连沿用原配置，显式改配保留前后版本及生效边界 |
| R26 Harness 运行纪律 | 长程协作依靠明确状态和边界持续工作 | 指令与能力按来源/作用域管理、上下文按需装载、原生运行与平台调度各有唯一责任；恢复有界且不叠加重试，独立验证和交接保留工作语义 |

R05 要验证 Lead 的真实协调过程，不能仅用一个预写任务队列代替。R11 首片沿用“状态展示 + 单测试会话显式托管”，逐项源码归属与后续探测/保活范围见 [功能归属清单](netcap-feature-ownership.md)。

插件形态可以不同：有的增加页面，有的提供工具或执行者，有的提供任务自动化。共同需求是共享平台中的对象、状态和交互规则；不把所有能力强塞进同一种模型工具插件。接口和实现形式属于下一阶段设计。

## 6. 怎样判断长程任务和角色协作是否有用

“大项目”暂不写成固定代码行数。更有代表性的验收任务应包含多个相关模块、现有约束、真实测试及需要交接的上下文。

“长程”至少包含三个维度：任务跨多轮、执行状态可恢复、验收结果可追溯。运行很久但没有可核对产物，不能证明该需求满足。

建议选择用户的一个真实开发任务，比较：

| 观察项 | 验收关注点 |
|---|---|
| 人工介入 | 还需要多少次手工催促、复制上下文、切终端和整理结果 |
| 交付质量 | 完成条件是否满足，原有功能是否通过相关验证 |
| 恢复能力 | 一次断线或重启后，完成项和修改是否保留，是否重复派发 |
| 协作收益 | 多 Agent 是否减少人工分工和汇总负担，是否增加冲突和返工 |
| 成本 | 可观测用量、耗时、并发和机器资源是否符合用户约束 |

具体耗时、预算、并发数和性能阈值尚未确认，不能先许诺“连续两天”“几十个 Agent”或精确提效比例。

## 7. 建议的分阶段范围

用户已明确 Lead 驱动的角色协作、各角色可选 CLI、新建与接续以及插件化。第一版可用产品必须覆盖这些目标，下面只是内部验证顺序。

| 阶段 | 用户获得的结果 | 不足以宣称什么 |
|---|---|---|
| 入口可行性 | 两类 WSL CLI 各自通过新建、实时接入、暂停后恢复，共六个入口场景 | 只实现工作台自己创建的会话，不能宣称入口齐全；暂停恢复不替代实时接入 |
| 插件纵切 | 当前项目的一项真实能力作为插件，在同一工作台使用 | 只有插件目录和加载演示，不能宣称业务已插件化 |
| 角色可行性 | 四类角色各自使用 Codex 和 Claude，验证职责与关联 Skill/Gate | 八种配置能保存不等于八种组合都能实际运行 |
| 长程闭环 | 一项开发任务跨轮推进、异常恢复、验证并交付 | 还不能宣称四类角色已能协作交付 |
| 协作闭环 | Lead 根据目标组织探索、实现、审查，并处理一次有证据的打回 | 预写固定清单不能代替 Lead 协调，固定场景通过也不等于任意规模团队都可靠 |
| 产品验收 | 从桌面提交目标，经过角色协作与人工介入取得验证后的结果；相关能力可扩展 | 单项协议验证不代替完整日常使用流程 |

首期应覆盖一个有代表性的目标，验证 Lead→Explore→Implementer→Reviewer 的协作、打回修复、一次中断恢复和一次人工接手。既验证 Codex/Claude 混合使用，也验证同一种 CLI 承担不同角色；不以常驻角色数或进程数作为验收指标。

暂不作为本次新需求的必需项：手机端、多人权限平台、多机器调度、公开插件市场、任意 Windows GUI 自动化、自动发布。它们尚无明确使用场景。

原项目已有的 OpenCode、路由保活、天气和通知等功能保持原有任务范围；本次需求分析不把它们自动升级为新产品首期条件，也不取消既有要求。

## 8. 与现有项目的关系

[现有工作台说明](../CONSOLE.md) 和 [实施进度](../goals/PROGRESS.md) 记录了三类工具会话、审批、恢复和 Web 的已有工作，新的任务编排仍在实施。这些是可复用能力，不是最终需求已满足的证明；本次未重跑产品验收。

上一轮“保留 netcap 作为平台核心、DSH 做插件”的默认建议需要调整。用户要求当前项目作为平台中的功能插件，后续应评估合适的桌面与插件底座，再判断既有代码如何复用。

当前项目的功能必须先拆清归属：哪些是可选业务能力，哪些依赖平台提供的会话、执行、状态和交互能力。用户要求的是“可作为插件使用”，不等于必须把每行已有代码放进同一个插件，也不要求把 Go 全部改写为其他语言。

选择底座时以四个硬条件对照：Windows/WSL 体验、两类 CLI 的新建和接续、角色协作与 Backend 自由组合、插件扩展。若某个候选不能覆盖已确认场景，应明确补齐成本或判为不满足，不能通过缩减需求让它看起来合适。

现有 Runtime 按编码工具接入，会话消息中的 `role` 表示对话消息身份；这不等于本轮定义的协作 Role。角色/Profile/Skill/Gate 是待落实的新需求，本轮只记录词汇与行为，不改运行代码。

## 9. 已确认决定与剩余问题

本轮用户已回答：

1. 统一工作台，类似 DeepSeek Harness 桌面端；以后通过插件加功能，当前项目应当成为其中一个插件。
2. 新建任务和接续已有终端任务，两种都必须支持。
3. 给出目标，由 Lead / Coordinator 组织 Explore、Implementer、Reviewer / Verifier 协作；Lead 尽量不大量改代码。

第二轮用户确认：实时接入原 CLI 和暂停后恢复原会话，两种交接方式都需要。

角色澄清进一步确认：四类角色和所有专家 Profile 都可选 Codex 或 Claude CLI；专家能力通过 Agent Profile + Skill + Gate 组合。当前追问仅涉及 CLI 选择由用户固定、由 Lead 在候选范围内决定，还是提供两种模式。

第三轮新增确认：每次执行选配 Skill/MCP/CLI 插件、多份供应商配置并发且会话隔离、共享与 CLI 专属能力管理、两类插件区分，以及 Harness 设计原则。CLI 执行配置与角色配置分别建模；Claude 仅更换 settings 文件并不自动隔离状态，产品需同时解决状态目录和进程环境绑定。

后续用一个真实任务样例确认交付标准、并发/费用约束，以及现有项目作为插件的第一项功能。平台选择和工程目录在这些条件下重新评估，不在需求阶段先行锁定。

## 10. 开源研究对需求和选型的影响

本轮核查了 11 个候选项目，并追踪 AionUi 的独立后端 AionCore。完整的 Star、许可、维护状态、固定 commit、源码路径和引用见 [研究报告](open-source-platform-survey.md)。本节只保留影响需求的结论。

**没有候选已被证明完整满足全部条件。** 建议优先对照 AionUi/AionCore 和 Untrivial-ai Agent Orchestrator；CAO 用于原生 CLI 角色协作实验。这个顺序不是底座决定，也不要求把三套系统叠加部署。

| 候选 | 值得验证的资产 | 必须补齐或证实的部分 |
|---|---|---|
| AionUi + AionCore | Windows 桌面、Leader/Teammate、Codex/Claude、扩展 manifest 和设置入口 | WSL 目标；写任务隔离；Explore/Reviewer 约束；Core 冷恢复目前回到 Idle，轮中状态不保留 |
| Untrivial-ai Agent Orchestrator | 独立 Orchestrator/Worker/Reviewer 配置、worktree、目标 SHA、TUI/Chat 持久交接 | 当前 Go 版已移除第三方 npm 插件；WSL 未证实；平台内交接不能代替外部 CLI 接管 |
| AWS CAO | role/provider 分离、tmux 原生 CLI、消息委派、workflow journal | Windows 桌面；插件业务入口；worktree 默认未启用；停止清理的产物保留；双 CLI 接续实测 |
| Emdash | Windows 桌面、两种 CLI resume、持久工作区服务 | WSL 专用入口、完整 Lead 协作和可安装业务插件契约未证实 |
| DeepSeek Harness | 插件服务组合、生命周期、Web UI | 当前原生 Codex/Claude provider 为 one-shot 临时委派，不能直接满足可续行角色与原会话接续 |
| ZCode | WSL 发行版、用户、路径与远程环境处理 | 自身 Agent runtime 不证明能管理两类原生 CLI 的既有会话 |

Vibe Kanban 虽有较高 Star，但当前 README 已宣布 sunsetting；Superset 当前未提供 Windows，许可为 ELv2；Happy 的 wrapper 和切换重启机制适合交接参考，但不证明能无准备接管任意已运行 CLI。Augani 的小型编排器保留作设计参考，不能忽略其当前 Codex coordinator/review 假设。

由此保留以下选型原则：

- **不以支持 Agent 数量代替角色协作。** 要观察 Lead 的真实委派、Reviewer 打回和最终 Gate。
- **不以名为 plugin 的内部模块代替功能插件。** 要观察安装、启用、设置、数据和平台对象的复用。
- **不以保存历史代替恢复。** 要判断原请求是否执行、原工具是否还运行、原控制器是否仍持有输入权。
- **不以 Windows 可启动代替 WSL 可用。** 项目、Git、CLI、配置与工具的实际执行位置必须一致且可核对。
- **不以主分支代码代替发行版能力。** 实测记录产品、后端、CLI、插件版本；拆仓组件要验证配套版本。

## 11. 建议补充的验收细则

### 11.1 六种入口分别验证，接入前提单独记录

| CLI | 工作台新建 | 原 CLI 正在运行时接入 | 原 CLI 暂停/退出后恢复 |
|---|---|---|---|
| Codex | 所选 CLI 和配置启动真实会话 | 观察并操作原 thread/执行器，在途任务保持连续 | 恢复原 thread 和项目上下文，不静默 fork/new |
| Claude | 所选 CLI 和配置启动真实会话 | 观察并操作原 session/执行器，在途任务保持连续 | 恢复原 session 和项目上下文，不静默创建无关联会话 |

每个“已有任务”样本都记录：是否在启动前已使用 wrapper、tmux、共享服务或其他插件；运行版本；是否切换进程；是否保留在途工具与审批；终端返回路径。分别测试独立启动的 CLI 与事先托管的 CLI，不能只拿后者证明前者通过。

实时展示和实时输入分别记录。仅读取日志可满足部分观察，不能据此标记可操作；同一原生会话 ID 也不能独自证明没有第二个执行者。Codex App Server 提供可研究的共享连接入口；Claude 官方 Remote Control 有特定客户端与认证条件，尚不能当成本工作台已取得通用接管能力。官方事实和来源见研究报告第 8 节。

若某一严格实时入口在已调查版本中不可行，应保留 R02b 未满足状态，并呈现具体接入前提与替代方案供用户决定；不能在技术选型时自动把它降为“恢复历史”。

### 11.2 八种角色组合与真实打回

四角色分别运行 Codex 和 Claude，共八种组合；同时覆盖一种混合 CLI 团队和一种全同 CLI 团队。检查的是行为，不只是下拉框能否选中。

- Explore 能读代码、查资料，不能因开放通用 shell 而获得未约定的业务写入；其研究产物交给其他角色使用。
- Implementer 获得明确目录、基线和修改范围；并行任务发生范围冲突时有可观察的处理。
- Reviewer 使用独立工作上下文，对明确版本的改动检查；实际测试与审查结论分开保存，不把没有运行的检查写成通过。
- Lead 根据真实发现和验证结果安排下一步；一次真实未满足条件被打回、修复和重新验证，依赖任务不能提前当作验收完成。

### 11.3 恢复不确定性和人工接手

| 故障／操作 | 需要观察到的结果 |
|---|---|
| 只关闭界面 | 执行层按约定继续；重开看到同一执行与进度 |
| 工作台断连，但原 CLI 仍运行 | 重连核对原执行；不再启动另一个 CLI 来“恢复” |
| 消息已经执行，确认响应丢失 | 核对原消息/轮次及结果；不因超时直接重复发送 |
| 在工具执行或等待审批时崩溃 | 能恢复原状态则继续观察；证据不足则显示待核对，不能直接当空闲 |
| 用户从终端接手 | 后续自动调度停止；在途动作和未决输入清楚显示 |
| 停止任务、禁用插件 | 已有改动和验证结果保留；清理 worktree 是单独动作 |
| 验证通过后产物又改变 | 标记相关旧证据不再覆盖当前产物，并重新运行受影响 Gate |

不预设必须用某种数据库、事务模型或租约实现这些结果；技术设计应能解释并验证消息重复、恢复和控制权竞争的处理。

### 11.4 netcap 插件的最小纵向验证

功能盘点已完成，首片采用实施计划已有的“状态展示 + 单测试会话显式托管”默认，因为它同时触及用户入口、平台会话、自动发送及恢复；底座接口与真实插件贯通仍待 W04 验证。

第一片只展示真实状态与设置，可验证扩展加载；第二片在用户选定的测试会话上启用功能，显示所属 CLI、配置、托管状态与实际消息记录；第三片验证人工接手、平台重启与插件禁用。只有完整路径通过，才能宣称该功能成为平台插件。

建议平台负责会话身份、执行入口、控制权与公共事件，插件负责其业务配置和托管策略；具体归属需对照选定平台的公共接口设计。无论采用何种划分，都不能让平台和插件各自无条件发送“继续”或维护互相矛盾的任务完成状态。

这些细则没有扩大到公开插件市场、多人调度或自动发布。下一阶段仍先验证入口和插件边界，再决定底座与改造目录。

## 12. 多执行配置与能力管理细则

### 12.1 配置隔离不是只有供应商下拉框

软件支持注册用户已有的 Codex 配置目录和 Claude settings 文件，并说明哪个 WSL 环境、原生状态目录和凭据来源参与执行。Claude 默认文件名是 `settings.json`，自定义文件可以有自己的名称；官方 `--settings` 是覆盖层，缺省项仍可能继承。需要会话隔离时还要绑定独立配置/状态目录，例如版本支持的 `CLAUDE_CONFIG_DIR`；具体保证依实测，不能仅凭两个 JSON 文件宣布隔离。

Codex 的 `CODEX_HOME` 区分本地配置和状态，但用户/项目 Skill、外部凭据设施等仍有其他来源。软件必须盘点并显示实际资源来源。会话按执行环境、状态命名空间和原生 ID 联合定位；同一目录的不同别名标为共享，不伪装为隔离。

A/B 配置同时运行时分别验证会话消息、供应商请求归属、能力加载和恢复。不同供应商会话仍可能修改同一项目，因此会话隔离不替代工作区隔离。原生配置目录、供应商选择与权限沙箱也不是同一个开关。

### 12.2 能力库和执行绑定

能力库至少区分“共享 Skill/MCP”“Codex Skill/CLI 插件”“Claude Skill/CLI 插件”；同一 MCP 定义可产生不同环境、凭据和权限下的连接。共享表示复用资产，不表示共用带状态的进程、账号或对话。

每次新建/派发有能力选择；继续原会话时也能提出调整，但须明确何时可生效以及是否需要重启。原生能力不支持时保留原配置并说明缺口，不静默放宽排除要求、替换会话或改变供应商。选中 Skill 不等于已经调用它；支持程度、可发现、实际加载和使用情况分别展示。

CLI 插件带入的 Skill、MCP、hooks 等按来源展开；不可拆分的组件不能伪装成独立可取消。项目和管理策略仍按原生规则生效，不能为了模拟资源白名单删除项目规则。实际无法排除的可选资源必须明确指出，该组合不能算严格选配通过。

资源更新、同名冲突、路径/脚本依赖、插件间重复 MCP 和在途热更新有明确处理；原生配置的合并规则由各适配器分别核对，不能采用统一“最后写入覆盖”。快照不保存明文凭据，导出资产不夹带会话和账号状态。

### 12.3 新增验收样例

| 场景 | 通过依据 |
|---|---|
| Codex A/B、Claude A/B 并发 | 四份执行配置分别使用预期路由与会话状态；停止一份不影响另外三份，重启仍恢复正确关联 |
| 相同原生会话 ID 出现在不同命名空间 | 软件区分两者；按原归属读取、发送、恢复，不能只凭 ID 合并 |
| 同角色、同项目两次采用不同能力 | 每次清单和实际可用工具相符，配置文件/进程环境互不覆盖 |
| 同一个共享 MCP 采用两份凭据/不同 cwd | 执行连接及工具结果归属正确；不默认共享认证或可变状态 |
| 未选择项目自动发现资源或插件隐含资源 | 展示继承/隐含来源并核对排除；不能排除则说明限制，不假装选择已生效 |
| 更新共享 Skill、CLI 插件或原生配置 | 旧执行保留原版本，或准确检测漂移并暂停受影响动作；新执行采用明确的新版本 |
| 压缩上下文或恢复原会话 | 保留目标、当前任务、权限/能力约束和证据引用；平台不自行重复原生恢复或清空历史 |
| 分别停用平台插件与 CLI 插件 | 影响范围正确，进行中的动作有交代，会话和产物未被隐式删除 |

原型和底座评估应增加这些场景。前轮候选排序尚未证明 R21–R26 已满足，不能直接沿用“有插件/多 Agent”作为通过依据。
